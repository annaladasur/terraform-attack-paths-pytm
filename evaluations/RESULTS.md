*Hop coverage* counts, for each hop of each gold path, whether a tool reported a finding on that hop's causal evidence (e.g. the 0.0.0.0/0 rule for an EXPOSES hop, IMDS for an ASSUMES hop, a wildcard grant for an ALLOWS hop). It is a generous measure: a finding on the hop is not the same as connecting the hops.

\* For C', a hop counts when a threat the plan *decides* (fires whatever the undecided controls are) is linked to it. This is not an independent measurement: the cloud pack's attributes are derived from the same graph the path engine uses. What it shows is that pytm, once fed evidence, can speak about the hops; C shows what it says without evidence.

## Verified remediation (A1)

For each attack path (at most three per fixture), the patch author (`simulated`) proposes one edit; the pipeline checks it against the edit policy, applies it to a copy, re-plans offline and re-runs the path engine and pytm. Only a proven effect is accepted; nothing is applied.

| Metric | Result |
|---|---|
| Paths attempted | 14 |
| Verified fix that breaks the path | 10 (71.4%) |
| Verified downgrade only | 1 |
| No verified fix (the author gave up or every proposal was rejected) | 3 |
| Proposals / rejected by the edit policy or the re-run / not verifiable (no plan) | 22 / 2 / 0 |
| Static what-if agreed with the re-planned effect | 17 of 17 |

The simulated author is a deterministic strategy (IMDSv2, then narrow the grant, then restrict ingress), so these numbers measure the *verifier* and the plan cache, not a model. Offline plans do not run AWS-side validation: a verified patch can still fail at apply time, which is one reason a human applies it.
